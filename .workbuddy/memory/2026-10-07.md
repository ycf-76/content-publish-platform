## 内置浏览器 vs 主流 AI 浏览器：差距分析

大哥问「内置浏览器跟别家 AI 工具的浏览器差在哪」。产出 `outputs/内置浏览器差距分析与改造清单.md`。

结论：差距不在功能数量，在两条地基——
1. **输入是合成事件**：`routers/browser.py:233` 用 `page.evaluate` +
   `elementFromPoint().dispatchEvent(MouseEvent)` → `isTrusted=false`，
   缺 mousedown/mouseup/focus 序列 → 下拉、日期选择器、hover 菜单、contenteditable
   工具栏、`<select>` 全打不中；`type` 依赖 `document.activeElement`，而合成 click
   不一定改焦点。改 `page.mouse.click/type/press` 即可（一行级收益）。
2. **没有等待与结构化**：全是固定 sleep（0.2/0.3/0.5s）+ 像素坐标盲点；
   别家是 ref 编号 + wait_for + 视觉标注。

实锤的坑：
- **ref 体系是断的**：MCP tool 描述说 snapshot 返回 ref（如 e3），但 `snapshot()`
  返回 a11y 树、**没有 ref**；`act()` 却把 ref 当 CSS 选择器（`page.locator(ref)`）
  → 外部 MCP 客户端按文档用必然失败，这条链路大概率从没跑通过。
- **nav_seq 是死参数**：api 收了、签名也收了（`client.py:512`），函数体一次没引用，
  snapshot 也不产出 → 对外宣称的「防陈旧点击」不存在。
- **多用户共用一个 page**：`get_browser_client()` 进程级单例 + 单个 `self._page`，
  `_lock` 只保护初始化 → 多人并发直接串场。
- **必死死锁（已修）**：`_ensure_initialized()` 在 `async with self._lock` 内部调
  `_switch_profile()`，后者回调本函数再拿同一把 asyncio.Lock → **不可重入，永久自锁**。
  已抽出 `_do_launch()`、把切换挪到锁外，代码里写了原因注释。

P0 四条：原生输入替换 / 点击后等 DOM 稳定 / 实现真 ref / 落地 nav_seq。
前端坐标换算（`ContextSidebar.vue:578` naturalWidth/rect.width）写得是对的，别动。

## 求证：主流 AI 浏览器都不是「截图 + 合成 DOM 事件」

联网查证过（省得下次重复查）：

- **Claude Computer Use**（platform.claude.com 官方文档）：截图 + **OS 级真实键鼠**，
  参考实现是 `xdotool mousemove/click/type`（X11/Quartz/Win32）。
  官方原话："no hidden browser automation; the model only sees pixels and emits coordinates"。
- **OpenAI Operator / CUA**：截图 → CoT 推理 → **虚拟鼠标键盘**执行 click/type/scroll，
  跑在云端容器里。WebVoyager 87% / WebArena 58.1% / OSWorld 38.1%。
- **Playwright MCP（微软）**：核心工具 **明确不用视觉与坐标**，只用 a11y 树 +
  `[ref=e2]` → Playwright Locator → `Input.dispatchMouseEvent`。
  本项目 MCP 描述里的 ref 概念就是照它抄的，但实现没兑现（snapshot 不产出 ref）。
- **Browser Use**：DOM → 整数索引 → CDP `Input.dispatchMouseEvent`；截图是**条件性**的
  （只在需要视觉时截），以 DOM 分析为主。

结论：**没有任何一家用「截图感知 + JS 合成事件」**。这个组合恰好是
「第二代的成本 + 没有第二代的能力」。`isTrusted` 是规范里**只读**的原生属性、
伪造不了，所以这条路从设计上就封死，不是运气问题。

另外：**浏览器实例的创建方式本项目没落后**（persistent context + headful + profile
持久化是标准做法，比 Computer Use 的 VM/Xvfb 还轻）。落后的只有「感知」和「输入」两层，
不用推倒重建。Anthropic 自己在 Cowork 里也把优先级定为
连接器 > 内置浏览器 > 屏幕交互，截图操作是最后兜底。

## 产品决策：谁来决定骨架？（大哥要的产品视角分析，已产出结论）

大哥的两难：「用户拍板 → 后期模板多了不好处理」「LLM 决策 → 达不到预期」，两边都有问题，要我拍。

### 拆解（两边的问题其实都不是"选错"）
- **用户拍板的真问题不是"烦"，是模板膨胀后选择过载** —— 今天 6 个、明天 20 个，用户会被淹。
- **LLM 决策的真问题不是"选错"，是"不可预期"** —— 同样输入两次给不同结果，
  用户形不成心智模型 → 不信任 → 反复重做。

### 结论：三层架构（已与大哥对齐前的分析结论）
| 层 | 谁决定 | 决定什么 | 数量 |
|---|---|---|---|
| 用户层 | 用户 | **意图**（干货清单型 / 教程型 / 测评型…），不是模板 | **锁死 ≤7 个**（7±2） |
| LLM 层 | LLM | 意图 → 具体版式、页数、图片位（它有内容信息优势） | 系统内部 |
| 模板库 | 系统 | layout_id / recipe，可无限增长 | 用户永不直接面对 |

**模板膨胀的解法不是限制模板，是把用户和模板隔开**：用户只接触稳定的意图层（≤7），
模板在系统层随便加，不影响用户界面。

### 更关键的一条：把「可撤销」做扎实，比把「事前选择」做重更值
- 我们有结构化 deck，**内容独立于版式** → 「换骨架」可以做到**内容零丢失**
- 当切换成本趋近 0，事前选择的精度要求就大幅下降
- 这是 Easel 做不到的（它出图即死 PNG）——**我们的杀手锏**

### 对之前「when=always 每次都问」的修正（已提给大哥）
改为 **when=missing + 常驻切换器**：
- 首次/无偏好时问一次 → 选完存进 profile 记住 → 之后不打断
- 成品上常驻「换骨架 / 换风格」一键切换（带预览、内容不丢）
- 理由：大哥要的"让用户拍板"实现了，但不必每次打断；控制感靠常驻切换器保证，
  不靠事前拦截。

## 会话惰性落库：没发消息就不产生会话（已改完并通过编译）

大哥报：「点创作底下的作品，不管有没有发布内容都会多一个会话」。根因：

- `useChatActions.newConversation()` **一进来就调 `createSession`**，还会 `addConversation` 写进
  history → 「新建对话 / switchToFolder / switchToWorkConversation / selectFile」四条入口，
  只要**进入**就落库一条空会话。
- 而 `useChatAgent.sendAgentMessage` 里本来就有一段「没有 sid 就补建 session」的逻辑
  → 落库这件事被做了两遍，第一遍是多余的。

改造办法：**引入草稿态会话**
- `Conversation` 增加 `_isDraft / _folderId / _workId`（`cell-types.ts`）
- `newConversation()` 只建内存草稿（`id = draft_xxx`）、**不建后端会话、不进历史**，
  `activeSessionId` 强制置 null（否则第一条消息会挂到上一个会话上）
- 新增 `ensureSession(title?)`：唯一的落库出口，把草稿 id 换成真 sessionId + 写 history
- `ChatView.sendMessage()` 在 **push user 消息之前** await `ensureSession()` ——
  顺序不能反，反了 updateTitle / 后端 updateSession 就对不上草稿 id
- `useChatAgent` 里那段自建 session 删掉，改成调同一个 `ensureSession`；
  再加 `linkSession(sid)` 兜底：前端落库失败、后端自己在 agent 响应里返回 session_id 时，
  把还挂着草稿标记的 conv 对上号并补进历史
- `switchToFolder` / `switchToWorkConversation` 加「**复用当前空草稿**」分支：
  草稿不进 history，`getConversationsForFolder/Folder` 查不到它，连点同一个作品/文件夹
  会不停新建草稿把用户已输入内容冲掉
- `watch(activeConvId)` 和 `switchToConversation` 加草稿短路：
  草稿 id（`draft_xxx`）绝不能拿去打 `listMessages` / `loadFilesForSession`
- `newConversation` 顺手清掉其它空草稿，避免 conversations 无限增长

验证：`vue-tsc -b --force` EXIT=0（注意 `-p tsconfig.app.json` 会报一屏假错——
**paths 别名只定义在根 tsconfig.json**，app 那份不 extends 根，别被误导）；
Vite JS API 打包冒烟 BUILD_OK（产物丢进 %TEMP%，不碰 dist）。

验收动作：点作品 / 新建对话 → 左侧历史**不出现**新条目；发第一条消息后立刻出现，
标题 = 用户首条消息前 200 字。

### ⚠️ loop.py Stage 0 澄清机制的三个硬约束（踩过才知道）

1. **澄清字段名必须与工具入参名一致**。`loop.py` 用 `_fname in arguments` 判断「LLM 是否已明确」，
   名字对不上时：LLM 明明传了 `recipe_id` 仍会被拦下问一遍，且澄清结果也灌不进工具入参。
   （我一开始写成 `card_recipe`/`card_theme`，后来改成 `recipe_id`/`theme_id`/`image_layout`。）
2. **`auto_default=True` 的真实语义 = 不打断**：注入默认值继续执行，只推一张非阻塞的
   `agent_clarification_hint` 建议卡。所以想「真正让用户拍板」必须 `auto_default=False`。
   本方案取舍：骨架/风格 False（核心价值，第一次必须选），图片用法 True（技术性强，走默认）。
3. **`when=missing` + 已答过 → 自动跳过**（判定 `_fname in _already_clarified`），
   这天然实现了「第一次问、之后记住」，不用自己做记忆逻辑。
   另：`node_type` 必须在 `_CLARIFY_TRIGGER_NODE_TYPES = {produce, create, design, generate, copywrite, card_design}`
   里才会触发 —— 我们的 `node_type="produce"` ✓。
