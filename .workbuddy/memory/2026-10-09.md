### 为什么昨晚那版没效果（关键教训）

**改了但稳态等价，等于没改。** 旧模型 `cps = backlog / lag` 和昨晚新模型
`cps = base × sqrt(backlog/soft)` **都是追赶模型** —— 稳态必然收敛到
「显示速率 = 后端产出速率」。平滑得再好看，稳态速度完全一样，用户感知不到差别。

结论：**要 codex 那种匀速，必须彻底脱钩 backlog**，按固定速率吐，让积压自己排队。
只做「平滑追赶」是自欺欺人。

### 本轮实际改动

`composables/useChatSSE.ts` tick：
- 正常阶段 `target = baseCps` **恒定**，不看 backlog；
  只在 backlog > `max(1200, base*3)`（约 3 秒缓冲）才温和加速、上限 1.4×。
- 收尾 `pendingSettle` 从 `backlog/0.12` 改成 **`2.2×base` 封顶**：
  旧写法在积压几千字时算出几千 cps，表现为「前面慢慢吐、最后一坨全涌出来」——
  这才是「涌现」最明显的来源，昨晚漏掉了。
- 保留：dt clamp 0.10s、1/120s 固定步长累加器、cps 指数缓动（tau=0.32）。

## ReAct 主循环截断问题（只讨论，未改代码）

大哥提出：loop 用 `for` 提前限定最大次数 → 任务被截断、用户不知情，
认为 ReAct 不该预先限定执行次数。

**结论：`for` 改 `while` 是伪命题，不要做。** `for i in range(n)` 与
`while i < n` 语义等价，换成 while 只要还是 `while iteration <= max_iterations`，
行为一字不变；改成真无限 while 更危险（LLM 陷入「搜索→不满意→再搜」时
token 烧穿 + 请求永不返回，客户端超时比截断更惨）。ReAct 原论文与
LangChain/OpenAI Agents SDK/Claude Code 全都有 max_steps。

**真正的病根有三处（按优先级）：**
1. **模型不知道自己快没步数了** —— `_call_llm_streaming` 内已注入
   `harness.time_reminder`（时间预算），但**没有 iteration 预算提醒**。
   LLM 不知道只剩 2 轮，自然不收敛。这是「跑满截断」的主因。
2. **截断信号被前端吞了** —— `frontend/src/components/chat/agent-output-formatter.ts:32-39`
   的 `INTERNAL_KEYS` 把 `_loop_truncated` 列为内部字段直接丢弃。
   后端 loop.py:824-839 明明写了「任务已执行 N 轮，但未收到 final 信号」，
   用户一个字看不到。**这是大哥说的「用户不清楚怎么回事」的直接原因。**
3. **截断后不能续跑** —— `save_loop_state` 只在 confirmation/clarification
   分支调用（loop.py:750-823），截断分支没落盘，用户只能重发。

### 关键位置备忘
- 主循环：`backend/app/engine/harness/executor/loop.py:405`（`for iteration in range(1, _max_iter+1)`）
- 跑满兜底：`loop.py:824-839`（`for/else`）
- 上限常量：`loop.py:49-59`（`_DEFAULT_MAX_ITER=20`、`_MAX_ITER_HARD_CAP=80`、`_DEFAULT_TOTAL_TIMEOUT=600`）
- 已有预算机制（别重复造）：`token_budget.py`（hard_stop_total=200000）、
  `context_window.py` + `context_compact.py`（87.5% 压缩）、
  `_tool_fail_counts`（同工具连败 3 次熔断）
- `codex/session.py:233-236` 有**同一套** max_iterations 兜底，改要一起改

### 建议方案（等大哥拍板）
A. 保留步数上限，降级为「软预算」+ 给 LLM 注入剩余轮次收敛提醒（跟
   time_reminder 同一注入点，loop.py:1695 附近）；
B. 截断分支也调 `save_loop_state`，返回续跑入口；
C. 前端把 `_loop_truncated` 从 INTERNAL_KEYS 摘出来，渲染成可见状态条。

## 【修正】上一轮结论被推翻：真正的病根是终止信号不可靠

大哥二次批判：「问题不在 for vs while，而在终止信号不可靠」。**他对，我上一轮只说到症状层。**

`for` 循环不是 bug，是**遮羞布** —— 遮的是「协议没有表达终止的能力」这个事实。
因为内生终止信号不可靠，外生的步数上限才被迫当主要终止手段用。

### 铁证：不存在结构化终止工具
`backend/app` 全目录搜 `finish` / `final_answer` / `complete_task` / `submit_final`
→ **零匹配**。于是通道不对称：
- 执行 → `api_tool_calls`（function calling，原生结构化）
- 终止 → `_parse_step(content)` 从正文文本嗅探

且 loop.py:603 终止检查写在 `if not tool_calls and content:` 内，
**只要模型还在调工具就永远无法终止**；模型想结束只能「停止调工具+说人话」，
这在结构上跟「卡住复述计划」无法区分。

### 三处不可靠（代码位置）
1. `_parse_step` loop.py:2132-2154：**三级降级且全静默**
   `json.loads(全文)` → 截取首个 `{` 到末个 `}` 再 parse → `{"raw_text": content}`
   最后一级返回体**连 `final` 键都没有**，信号蒸发，无一行日志。
   触发场景：JSON 前后带自然语言 / 输出两个 JSON 块 / 流式拼接截断。
2. `_PLAN_MARKERS` loop.py:1361-1366：23 个中英文过程词黑名单
   （我来/我会/正在/接下来/首先/第一步/我需要/let me/I'll/step 1…）
   判定：无 tool_calls + 非纯 JSON + **长度 <120 字** + 命中 marker
   → 判为「在说废话」→ 注入 `_tool_retry_prompt` **逼模型继续调工具**。
   **这是反向信号**：正常中文总结句极易同时满足「<120字」+ 含「首先/接下来」，
   已完成的任务被推回去继续跑。**这才是跑满 20 轮的最大制造源。**
   另：loop.py:1464 `len >= 120 → return False`，长总结反而安全，短总结被误杀，阈值是拍脑袋的。
3. 终止判断整体是**启发式驱动**（正则 + 关键词黑名单 + 长度阈值 = 在猜模型意图），
   不是**协议驱动**。`_PLAN_MARKERS` 的存在本身就是架构错误证据。

### 正确结构（内生 → 语义 → 保险丝）
现在是倒过来的：保险丝当主力。
1. 内生：注册 `finish` / `final_answer` 工具，让终止走与执行同一条可靠通道
   （LangChain AgentExecutor / OpenAI Agents SDK / Claude Code 都是这么做的）
2. 语义：停滞检测 —— 连续 N 轮 `called_tools` 无新增或 observation 重复 → 主动收敛
3. 保险丝：步数/时间上限保留但降级，触发率应从「主要手段」降到 <1%
   **衡量改造成功的唯一指标：`_loop_truncated` 触发率。**

另：删 `_PLAN_MARKERS`；`_parse_step` 每级降级 + plan 误判都要打日志上报
（现在全静默 = 盲飞，分不清是模型不听话还是解析挂了）。

`LAYOUTS` 是**硬编码 dict**，每个版式允许的 block 组合写死成元组：
```python
"list_ledger":    ("heading", "list"),      # 账本页塞不进 stat/footer
"content_text":   ("heading", "text"),
"quote_callout":  ("quote",),
```
→ 即便接上 DSL，一页里混搭 `stat + list + footer` 当前**不被允许**。
这是"组件不丰富"的第二层原因：不只是数量少，是**组合被冻结**。

### 根因（乘法 vs 加法）
- **Easel**：9 风格 × 6+ 骨架家族 × 10 个卡片 skill，共享 `card-design` 设计系统 → **乘数组合**；

- **大哥项目**：18 个写死页型彼此不组合 → **加法规律**；模板是 TS 枚举分支 / Python 元组 → **封闭集**。
