# 开发指南：防止代码膨胀与维护恶化

> 生成日期：2026-09-17
> 目的：每次写代码前按此指南检查，防止"随便堆叠代码导致项目臃肿"
> 原则：**做完一个再做下一个。每做完一个，跑一遍核心路径确认不回退。**

---

## 零、核心路径定义

**核心路径 = 用户真正会走的最短链路**：

```
搜索(search) → 分析(analyze) → 文案(copywrite) → 图片规划(image_plan) → 图片生成(image_gen) → 图片审核(image_review) → 终审(final_review) → 发布(publish)
```

**任何改动后，必须验证这条路径能跑通。** 这是你的"回归测试"。

---

## 一、新增功能前的 5 道关卡

在写任何新代码之前，依次回答这 5 个问题。**任何一个回答"否"，就先停下来解决那个"否"**。

### 关卡 1：这个功能属于核心路径吗？

| 答案 | 行动 |
|------|------|
| 是 | 继续，优先级 P0 |
| 否，但用户明确要求 | 继续，优先级 P1 |
| 否，我觉得以后可能有用 | **停下来，不写**。写到 TODO 列表里，等有真实需求时再写 |

**反例**：你写了 7 家 LLM 适配器"以后可能有用"，结果只有 DeepSeek 一家在用，其他 7 家是负债。

### 关卡 2：现有代码里有类似功能吗？

```
搜索方式：
1. SearchCodebase 搜关键词
2. 看 tools/registry.py 的 Skill 列表
3. 看 api/routers/ 的 Router 列表
4. 看 frontend/src/stores/ 的 Store 列表
```

| 答案 | 行动 |
|------|------|
| 有，但没做完 | **先做完现有的，不写新的** |
| 有，做完了 | 复用/扩展，不重复写 |
| 没有 | 继续 |

**反例**：你写了 `feishu_wiki_doc_skill.py`，但 `feishu_file_ops_skill.py` 还没做完。

### 关卡 3：我能用 100 行以内写完这个功能的 MVP 吗？

| 答案 | 行动 |
|------|------|
| 能 | 写 |
| 不能，因为需要 X/Y/Z | **先只写 X**，验证 X 能跑，再写 Y |

**反例**：`esther_factory/engine.py` 一上来就 600 行 + 129 个 TODO。应该先写 100 行的 MVP 渲染器，验证能跑，再逐步加功能。

### 关卡 4：这个功能加进来，会让已有功能变难改吗？

检查维度：

| 维度 | 检查方法 |
|------|----------|
| 新增 Store 依赖 | 如果一个组件依赖 > 2 个 Store，考虑合并或拆分组件 |
| 新增 lifespan 步骤 | 如果 lifespan > 8 步，考虑懒加载（首次请求时初始化） |
| 新增 Router | 如果 Router > 20 个，考虑模块化注册（按功能分组） |
| 新增 AgentHarness 参数 | 如果参数 > 8 个，改用 Builder Pattern |
| 新增 ChatView 内联组件 | **绝对禁止**。新组件必须独立 .vue 文件 |

**反例**：CrabCompanion / CatCompanion / SpongeBobCompanion 直接内联在 ChatView.vue 里，增加了 50+ 行模板和 20+ 行 ref。

### 关卡 5：我能在 30 分钟内写完这个功能的测试吗？

| 答案 | 行动 |
|------|------|
| 能 | 先写测试，再写功能（TDD） |
| 不能 | 功能太复杂，拆小 |

## 二、代码组织规范

### 2.1 后端文件大小限制

| 类型 | 上限 | 超过时 |
|------|------|--------|
| 节点函数 (agents/nodes/*.py) | 200 行 | 抽子函数到同目录的 _helper.py |
| Router (api/routers/*.py) | 150 行 | 拆子路由 |
| Service (services/*.py) | 300 行 | 按职责拆分 |
| Skill (tools/*.py) | 150 行 | 抽公共逻辑到 tools/common/ |
| Harness/Engine | 400 行 | 用组合模式替代继承 |

**当前违规文件**：
- `ChatView.vue`：5678 行（上限 500 行）
- `esther_factory/engine.py`：~600 行 + 129 TODO
- `image_plan_planner.py`：~400 行 + 94 TODO
- `recovery/loop.py`：~300 行 + 48 TODO

### 2.2 前端组件规范

| 规则 | 说明 |
|------|------|
| 单组件上限 | **500 行**（template + script + style 合计） |
| 单组件 Store 依赖 | **≤ 2 个** Store |
| 单组件 ref 数量 | **≤ 10 个** ref/reactive |
| 子组件通信 | props + emit，**禁止**直接访问父组件 ref |
| 跨组件通信 | 通过 Store 或 provide/inject，**禁止**事件总线 |
| 新组件必须独立文件 | **禁止**在父组件里内联定义子组件 |

### 2.3 后端初始化规范

| 规则 | 说明 |
|------|------|
| lifespan 步骤上限 | **8 步**。超过的用懒加载（首次请求时初始化） |
| 每步必须记录成败 | `startup_health[step_name] = True/False` |
| critical 步骤失败 | **抛异常，应用不启动**。不吞错 |
| non-critical 步骤失败 | 记录 + 功能降级，前端可见降级提示 |
| 禁止裸 try/except 吞错 | 必须 `startup_health[name] = False` + `logger.warning` |

## 三、新增功能的标准流程

### 3.1 后端新增 Skill

```
1. 在 agents/prompts/skills/ 下新建 .md 文件
2. frontmatter 必须设置 category 和 priority（见下方规范）
3. trigger_words 至少写 2 个（用于路由预筛匹配）
4. 如果需要 Python 脚本，在 tools/ 下新建 skill 文件（< 150 行）
5. 在 tools/registry.py 注册（一行）
6. 写一个最简测试（调一次，验证返回格式）
7. 在对应节点函数里调用
8. 跑一遍核心路径
9. git commit（message: "feat: add xxx skill"）
```

**Skill frontmatter 规范（必填）**：

```yaml
---
node_type: plan            # Skill 层级
name: my_new_skill         # 唯一标识（snake_case）
category: create           # 分类：create/analyze/operate/audit/dev/platform
priority: hot              # 优先级：hot/warm/cold
display_name: 我的技能      # 中文显示名
description: >-
  功能描述（≤200字）
trigger_words:
  - 触发词1
  - 触发词2
---
```

**category 选择**：
- `create`：生成内容（文案/卡片/图片/视频脚本/大纲/钩子）
- `analyze`：分析数据（诊断/复盘/竞品/趋势/评估）
- `operate`：管理运营（画像/排期/热点/策略/发布）
- `audit`：审核把关（质量门禁/合规/风险）
- `dev`：开发工具（文件/浏览器/工作流/脚本）
- `platform`：外部平台（微信/飞书/抖音API）

**priority 选择**：
- `hot`：高频核心，始终注入
- `warm`：中频按需，用户提到相关词时注入
- `cold`：低频，仅精确触发时注入

> 详细架构说明见 `docs/01-ARCHITECTURE.md` 第十二章「Skill 智能路由架构」

**禁止**：
- ❌ 写了 Skill 不注册（死代码）
- ❌ 写了 Skill 不测试（下次改就不知道对不对）
- ❌ 一个 Skill 做两件事（违反单一职责）
- ❌ .md frontmatter 不设 category/priority（路由无法分类）
- ❌ trigger_words 少于 2 个（预筛匹配率低）

### 3.2 后端新增 Router

```
1. 在 api/routers/ 下新建 router 文件（< 150 行）
2. 在 api/schemas/ 下定义请求/响应 Schema
3. 在 main.py 的 import 行和 include_router 行注册
4. 写一个 curl 测试（调一次，验证返回格式）
5. git commit
```

**禁止**：
- ❌ Router 里写业务逻辑（业务逻辑在 Service 层）
- ❌ Router 直接操作 DB（通过 Service 层）
- ❌ 注册了 Router 但前端没对接（死路由）

### 3.3 前端新增组件

```
1. 在对应目录下新建 .vue 文件（< 500 行）
2. 只依赖 ≤ 2 个 Store
3. 只定义 ≤ 10 个 ref
4. 通过 props + emit 与父组件通信
5. 在父组件里 import 并使用
6. 跑一遍核心路径
7. git commit
```

**禁止**：
- ❌ 在 ChatView.vue 里直接写新组件（必须独立文件）
- ❌ 新组件依赖 > 2 个 Store（拆分组件或合并 Store）
- ❌ 新组件 > 500 行（拆子组件）

### 3.4 前端新增 Store

```
1. 在 stores/ 下新建 .ts 文件
2. 定义 state + getters + actions
3. 在组件里 import 使用
4. 确认没有循环依赖（Store A import Store B，Store B import Store A）
5. git commit
```

**禁止**：
- ❌ Store 之间循环依赖
- ❌ Store 里写 DOM 操作（DOM 在组件里）
- ❌ 一个 Store 管超过 2 个业务领域

## 四、修改现有代码的规范

### 4.1 改之前

1. **读完整函数**：不要只看报错行，看整个函数的逻辑
2. **找所有调用方**：`SearchCodebase` 搜函数名，确认改了不影响其他
3. **确认测试存在**：如果没测试，先写测试再改

### 4.2 改的时候

1. **最小改动**：只改需要改的，不顺手"重构"其他代码
2. **不改接口**：如果必须改接口，先加新接口，再标记旧接口 deprecated
3. **不加新依赖**：除非必要，不引入新库/新 Store/新 ref

### 4.3 改之后

1. **跑核心路径**：搜索→分析→文案→生图→审核→发布，确认不回退
2. **git commit**：小步提交，每次 commit 只做一件事
3. **检查副作用**：改了 A，B 的行为变了吗？

## 五、半成品管理规范

### 5.1 什么时候可以开始写新功能？

**只有当所有 P0 和 P1 的半成品都完成后**，才能开始写 P2/P3 的新功能。

当前 P0/P1 半成品：
- [ ] ChatView.vue 拆分（P0）
- [ ] lifespan 健康度汇总（P0）
- [ ] WorkbenchView.vue 拆分（P1）
- [ ] AgentHarness 简化（P1）
- [ ] SSE Parser 适配器模式（P1）
- [ ] LLM 适配器收敛（P1）

### 5.2 半成品代码怎么处理？

| 情况 | 处理方式 |
|------|----------|
| 已写但未完成，且当前不需要 | 从启动链/路由注册中**注释掉**，代码保留在 git |
| 已写但未完成，且当前需要 | **停掉其他工作，先做完这个** |
| 未写但觉得以后有用 | **不写**。记录到 TODO 列表，等有真实需求时再写 |

### 5.3 恢复半成品的流程

```
1. 取消注释（启动链/路由注册）
2. 端到端验证（从 API 调用到前端显示）
3. 补测试
4. 清理该模块的 TODO/FIXME
5. git commit
6. 跑核心路径确认不回退
```

## 六、质量门禁

### 6.1 每次 git commit 前检查

| 检查项 | 标准 | 不通过时 |
|--------|------|----------|
| 核心路径能跑通 | 搜索→发布全链路 | **不 commit** |
| 没有新增 TODO > 5 个 | 新功能可以留 TODO，但不超过 5 个 | 减少 TODO 或拆分提交 |
| 没有新增 > 500 行的文件 | 见 2.1/2.2 | 拆分文件 |
| 没有新增裸 try/except | 见 2.3 | 加 startup_health 记录 |
| 没有新增 Store 循环依赖 | Store A → Store B → Store A | 重新设计依赖关系 |

### 6.2 每周检查

| 检查项 | 标准 | 命令 |
|--------|------|------|
| TODO/FIXME 总数 | 不增长 | `grep -r "TODO\|FIXME" backend/ frontend/src/ \| wc -l` |
| 最大文件行数 | < 500 行 | 见 2.1/2.2 |
| lifespan 步骤数 | ≤ 8 步 | 数 main.py 里的 `step` 标记 |
| Router 总数 | ≤ 25 个 | 数 main.py 里的 `include_router` |
| Store 总数 | ≤ 8 个 | 数 stores/ 目录下的 .ts 文件 |

## 七、架构决策记录（ADR）

每次做重要的架构决策时，记录在这里，防止"为什么这么设计"被遗忘。

### ADR-001：搜索节点不走 LLM

- **决策**：search_node 直接调 TrendingSearchSkill，不经过 LLM Loop
- **原因**：搜索是确定性动作（调 API 拿数据），不需要 LLM 推理，且节省 token
- **后果**：搜索节点无法做模糊理解，但这是正确的取舍

### ADR-002：图片生成交给前端

- **决策**：image_gen_node 只做校验+打包，生成交给前端卡片编辑器
- **原因**：服务端生成图片质量不可控，前端所见即所得
- **后果**：前端需要完整的图片编辑能力，这是正确的职责划分

### ADR-003：SSE 事件总线单进程

- **决策**：SSEEventBus 使用进程内 dict，不跨进程
- **原因**：当前单实例部署，Redis Pub/Sub 增加复杂度但无收益
- **后果**：多实例部署时需要改为 Redis Pub/Sub，已标注扩展路径

### ADR-004：工作流 interrupt 机制

- **决策**：5 个 interrupt_before 点把选择权还给用户
- **原因**：人在回路（human-in-the-loop），关键决策需要用户确认
- **后果**：工作流不是全自动的，需要用户交互才能推进

## 八、速查：什么情况该怎么做

| 情况 | 正确做法 | 错误做法 |
|------|----------|----------|
| 想加新功能 | 先检查 5 道关卡 → 通过后按标准流程写 | 直接开写 |
| 想加新 LLM 适配器 | 先验证 API key 可用 → 写适配器 → 写测试 → 注册 | 写了 8 家但只验证 1 家 |
| 想加新前端组件 | 独立 .vue 文件 → ≤ 500 行 → ≤ 2 Store | 内联在 ChatView 里 |
| 想加新 lifespan 步骤 | 加 startup_health 记录 → 标记 critical | 裸 try/except 吞错 |
| 想加新 Skill | < 150 行 → 注册 → 测试 → commit | 写了不注册/不测试 |
| 改了一个 bug | 跑核心路径 → commit | 改完就完 |
| 发现半成品 | 注释掉启动链 → 记录到半成品清单 | 留着不管或删代码 |
| 想重构 | 小步拆分 → 每步可验证 → 每步 commit | 推倒重来 |
| ChatView 又膨胀了 | 抽子组件到独立文件 | 继续加内联代码 |
| lifespan 又加步骤了 | 检查是否 > 8 步 → 超过则懒加载 | 继续加 try/except |
