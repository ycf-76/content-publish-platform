## 〇、方案决策（已定，P0 已实施）

**选 Playwright MCP 那条路（感知结构化 + CDP 原生输入），不追 Computer Use（截图 + OS 级键鼠）；但截图保留给人看。**

判断依据：
- 本项目是**多人系统 + 人也要用面板**，不是纯 LLM 自主浏览。Computer Use 要拖 VM/Xvfb，每步一次截图 + 推理，慢且贵，Windows 上部署成本还高。
- 你已经有 persistent context 的真浏览器，没必要降级到"看像素猜坐标"。
- Anthropic 自己在 Cowork 里也把优先级定为 连接器 > 内置浏览器 > 屏幕交互，截图操作是最后兜底。

所以是**双通道**：感知层分人/模型两条（截图+标注 / a11y 树+ref），**输入层统一走 Playwright 原生 → CDP `Input.dispatchMouseEvent`**。

## 一、核心结论

差距不在"功能少几个按钮"，而在**两条地基级差异**：

1. **操作不是真操作** —— 鼠标键盘是 JS 合成事件，`isTrusted = false`；主流工具全是 CDP 原生输入。
2. **没有等待与结构化** —— 交互靠固定 sleep + 像素坐标盲点；主流工具靠 ref/元素定位 + wait_for + 视觉标注。

这两条决定了：简单静态页能用，稍微现代一点的前端（React/Vue SPA、下拉菜单、日期选择器、富文本、 hover 才出现的按钮）就大面积失效。

## 二、逐条差距（附代码证据）

### 1. 输入合成 vs 原生（最致命）

`routers/browser.py:233`：
```python
await client.evaluate(f"() => {{ const e = new MouseEvent('click', {{ clientX: {x}... }});
    document.elementFromPoint({x}, {y})?.dispatchEvent(e) }}")
```

后果清单：
- `isTrusted = false`，网站侧可以直接判定为自动化脚本（反爬、风控）
- **没有 mousedown → mouseup → focus 序列**：`<select>`、日期选择器、下拉菜单、文件上传框、`contenteditable` 工具栏全部打不中
- hover 才渲染的菜单：直接 click 时元素还没出现在 DOM 里
- 不触发 `pointerdown` / `pointerup` 监听的现代 UI 库（Radix、Ant Design、Element Plus）无反应
- 跨 iframe 内容取不到
- `type` 依赖 `document.activeElement`（`browser.py:253`），而合成 click 不一定改变焦点 → 经常打到错误的输入框，或压根没焦点
- 无按键能力：没有 Enter / Tab / Esc / 组合键（`act()` 里有 press，但前端面板没接）

一行替换即可解决：`await page.mouse.click(x, y)`（自动滚动到可视区、等待可点击、超时重试、isTrusted=true）。

### 2. 等待策略：全是固定 sleep

| 位置 | 现状 |
|---|---|
| `routers/browser.py:235` | click 后 `sleep(0.3)` 就截图 |
| `routers/browser.py:246` | scroll 后 `sleep(0.2)` |
| `routers/browser.py:261` | history.back 后 `sleep(0.5)` |
| `client.py:goto()` | 只等 `domcontentloaded`，不等 SPA 首屏渲染 |

SPA 路由跳转后 0.3 秒内容大半还没上来，点第二次必然点到旧 DOM 或空位。Playwright 的做法是 `wait_for_load_state("networkidle")` + `locator.wait_for()` + `expect_navigation()`。

### 3. 元素 ref 体系是断的（MCP 对外声称有，实际不存在）

`routers/browser.py:641` 的 tool 描述写：
> 返回可交互元素列表（**带 ref 编号，后续用 ref 点击/输入**）… ref 来自最近一次快照

但 `client.py:384 snapshot()` 返回的是 `page.accessibility.snapshot()` —— 一棵 **a11y 树**，里面**没有任何 ref 编号**。而 `client.py:522 act()` 收到 ref 直接当 CSS 选择器用（`page.locator(ref)`），报错文案也写着"ref 参数（CSS 选择器）"。

**结论**：外部 MCP 客户端（Claude Code / Cursor）按文档传 `e3`，必然失败。这条链路大概率从没真正跑通过。

同理，`nav_seq`（第 654 行，描述"防陈旧点击"）：`act()` 的签名收了这个参数（第 512 行），但**函数体从头到尾没引用过它一次**，`snapshot()` 也不产出 nav_seq。宣称的防陈旧保护不存在。

### 4. 多用户共用一个浏览器 page（架构级）

`client.py:564 get_browser_client()` 是**进程级全局单例**，内部维护**单个** `self._page`。
在一个多人登录的系统里，A 用户导航到自己的小红书，B 用户的操作会直接打在 A 的页面上；`navigate` 和 `screenshot` 之间也没有 per-call 串行化，`_lock` 只保护初始化。

主流做法：Playwright MCP 是每个客户端会话一个 context；Browser Use 一个 agent 一套；Operator 每个任务一个云端容器。

### 5. 视觉侧：对着截图盲点

- 截图前不给元素画框，用户不知道哪里可点（Browser Use 的核心就是这个）
- 整屏 JPEG `quality=60`，文字发虚，给多模态模型识别准确率打折
- 每次操作 = 一次全屏截图 + base64 回传（~200KB+），延迟明显；没有"只截变化区域"
- 前端坐标换算写得是对的（`ContextSidebar.vue:578` 用 `naturalWidth / rect.width`），这点没问题

### 6. 完全没有的能力

| 能力 | 现状 | 影响 |
|---|---|---|
| console / 网络请求捕获 | 无 | 页面报错了两个字都看不到，排障靠猜 |
| Trace / 视频录制 | 无 | 出问题无法回放（Playwright tracing 原生支持） |
| 弹窗 dialog 处理 | 无 | 遇到 `alert/confirm/beforeunload` 直接卡死 |
| 文件上传 | 无（只有 publish 链路里有 `set_input_files`） | 面板里传不了图 |
| 下载 / PDF | 无 | — |
| iframe 穿透 | 无 `frame_locator` | 嵌套页面够不着 |
| 代理 iframe 模式 | `httpx` 简易反代（第 133 行） | 只支持 GET，无 WebSocket / POST 表单 / cookie 转发，复杂站点必失败（所以前端才要备一个"切换到远程浏览器"按钮） |
| cookie / storage 管理 | 无 API | 登录态只能靠改磁盘文件 |
| 地理 / 时区 / 权限模拟 | 无 | 与 stealth 配合时才需要 |

### 7. 顺带修掉的：一处必死死锁

`_ensure_initialized()` 原实现在 `async with self._lock:` **内部**调用 `_switch_profile()`，而后者会回调 `_ensure_initialized()` 再次获取同一把 `asyncio.Lock`。**asyncio.Lock 不可重入 → 永久自锁**，请求永不返回。
触发条件：并发初始化且前后 profile 不同，在多 profile（飞书/QQ/发布各一套）场景下命中率不低。

**已修**：抽出 `_do_launch()`，profile 切换挪到锁外执行，并在代码里写清了原因。

## 四、说句实在的

这套内置浏览器**骨架是对的**：域名白名单 + 审计日志单点强制（很多工具没有）、持久化 profile 登录态、还自带 MCP Server 对外暴露，这几个点比同类产品超前。

真正拖后腿的就是"用截图坐标 + 合成事件"这套交互模型——它是早期玩具级实现，没跟上 2024 年之后 ref/快照这一代方案。P0 那 4 条改完，体感会有代际差异，而工作量大概就是一个下午。

要动哪一档，你说了算。
