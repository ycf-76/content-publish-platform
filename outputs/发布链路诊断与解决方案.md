# 发布功能诊断与改造方案（scrapling 链路 / 内置浏览器）

> 诊断日期：2026-10-07 ｜ 全部结论基于本机代码、运行日志与实机探针，不靠推测。

---

## 一、一句话结论

> **更正（2026-10-07 20:20 重启验证后）**：初版把「scrapling 未安装」列为第一性死因，这个判断**不准确**。
> 实测运行中的服务进程确实是 `.venv`（15:38 起，20:10 已重启确认），而 `.venv` 里没有 scrapling；
> 但系统 `C:\Python312` 装了 scrapling 0.4.15 却**缺 `pydantic_settings`，服务根本起不来**——
> 两个环境都不完整。旧发布链路在 `.venv` 下确实会 import 失败，但**就算让它 import 成功，
> 也照样发不出去**（见根因 2/3/4/5）。真正无法绕开的是：**登录态从未建立 + 一次性上下文**。

**发布跑不通的根因是「链路设计」而不是「依赖缺失」**：一次性浏览器上下文让半自动模式物理上不成立、71 秒冷启动撞 60 秒超时、截图拿不到、以及小红书 cookie 绑设备指纹导致登录态无法迁移。

**内置浏览器里发布不了的原因是登录态从来没建立**：小红书创作者域名不在 `BrowserClient` 的「需要登录」名单里，因此走 headless + 临时上下文，打开就是 `/login?redirectReason=401`，而且 headless 根本没有窗口给你扫码。

代码已经按下面的方案改造完毕（已编译 + 实机冒烟通过），**剩下唯一必须人工做的动作：重新扫码登录一次**。

## 二、根因清单（含证据）

| # | 问题 | 证据 |
|---|---|---|
| 1 | **运行环境分裂**（次要） | 服务实际由 `.venv/Scripts/python.exe` 启动（20:10 重启确认，PID 39880）；`.venv` 有 fastapi/playwright/playwright_stealth/uvicorn/pydantic_settings，**但没有 scrapling**。系统 `C:\Python312` 有 scrapling 0.4.15，却**缺 `pydantic_settings`，uvicorn 起不来**（实测 Traceback）。所以旧代码在 `.venv` 下第一行 import 就失败；换成系统 python 也起不了服务 |
| 2 | **一次性上下文，半自动模式物理上不成立** | `StealthyFetcher.fetch()` 内部是 `with StealthySession() as engine:`，`page_action` 返回即关浏览器；而默认 `auto_submit=False`（半自动），前端 PublishCard 还提示「请在浏览器窗口手动点击发布」——`headless=True`，根本没窗口 |
| 3 | **截图永远拿不到** | 实机探针：`hasattr(Response, 'page') == False`（scrapling 的 Response 没有 page 属性）。`platform_publisher.py` 于是走 fallback，另起一个**裸 playwright chromium** 重开 URL 截图——另一个全新未登录会话，前端拿到的永远是登录页，看起来就像发布失败 |
| 4 | **冷启动 71 秒 vs 超时 60 秒** | 探针实测：一次 `StealthyFetcher.fetch()` 从 import 到返回 **71.1s**（patchright chromium 启动 + 指纹注入），代码里 `timeout=60000`，page_action 里还有约 10s 固定 sleep，超时是常态；且每次发布都重新冷启动 |
| 5 | **内置浏览器打开发布页必是未登录** | `client.py:30` `_NEEDS_LOGIN_DOMAINS` 只有 feishu/qq/slack/notion，**没有 xiaohongshu**；→ `navigate()` 取 `headless=True` + `profile_id=None`（临时上下文，cookie 不落盘）。日志实证：`[BrowserClient] Playwright browser initialized (headless=True)` + `GET https://creator.xiaohongshu.com/login ... redirectReason=401` |
| 6 | **发布回查接口永远返回 error** | `workflow.py:830` 依赖 `app.tools.mcp.xhs_client`，该模块已删除（启动日志：`MCP clients init failed: No module named 'app.tools.mcp'`）→ 永远 `status="error"`，不在前端终止轮询的状态集合里 → **发布节点永久转圈** |
| 7 | **旧 cookies 已失效** | `storage_states/xiaohongshu.json`（10-04）14 个 cookie，3 个已过期，`websectiga` 剩 0.2 天；探针实测：把 cookie 注入全新 profile 后访问发布页，**仍然 401 跳登录**（小红书 `web_session` 绑设备指纹，换浏览器即失效） |
| 8 | **虚假成功** | 旧版每个填表步骤都是 `except: logger.warning`，标题正文一个字没填进去也照样返回「内容已填写完成」 |

## 三、已完成的改造

### 1. 新增 `backend/app/services/publisher_session.py`
常驻持久化发布浏览器会话，替代 StealthyFetcher：
- Playwright `launch_persistent_context`，登录态落盘到 `backend/data/browser_profiles/publish_{platform}`
- 反检测用 `.venv` **已装的** `playwright_stealth 2.0.3` —— 不引入任何新依赖
- 默认**有头模式**（`PUBLISHER_HEADED=1`，设 0 可切回无头），半自动流程才真正可用
- 提供 `check_publish_state()`：`pending / published / failed / session_invalid / not_applicable`
- 单例复用 + 断线自愈 + `close_all_sessions()`（main.py shutdown 已挂上，避免残留 chromium 进程）

### 2. 重写 `backend/app/services/platform_publisher.py`
- 接入常驻会话，删掉 `run_in_executor` 里 71 秒的同步阻塞
- 截图来自**同一个页面**（`session.screenshot()`），不再 fallback 到另一个浏览器
- 新增 `need_login` 状态 + 真实 `fill_errors` 回传；标题正文都没填进去 → 直接判 `failed`，不再报虚假成功
- 无头 + 半自动组合直接拒绝并说明原因（不再给「请手动点击」的幻觉提示）
- 旧 storageState cookie 一次性迁移（探针证明小红书这批 cookie 已失效，保留逻辑只为兜底）

### 3. 打通内置浏览器 `backend/app/tools/browser/client.py`
- 新增 `bind_external_session()` **托管模式**：访问创作者平台时，内置浏览器直接复用发布会话的浏览器实例
  （不能另开实例——同一个 `user_data_dir` 会被 Chromium 锁冲突）
- `_cleanup()` / `close()` 在托管模式下只解绑不关闭，不会把用户正在点的发布窗口关掉
- 创作者域名自动放行 + 发布页导航返回 `logged_in` / `headed` / 截图

### 4. 路由与工作流
- `browser.py`：`/publish/navigate` 走常驻会话（真实截图 + 登录态状态）；`/publish/check` 查发布会话，不再看无关的内置浏览器页面
- `workflow.py`：`/publish/check` 不再依赖已删除的 MCP 模块，改为查发布会话 → 轮询能拿到终态，节点不再永久转圈
- 三处重复的 `PUBLISHER_URLS` 收敛为 `publisher_session` 单一定义

## 五、你必须做的一步：重新扫码登录

cookie 无法跨浏览器迁移（根因 7 已实测），所以：

1. 确认 `.env` 里没设 `PUBLISHER_HEADED=0`（默认有头）
2. 重启后端 → 前端点「打开发布页」→ **会弹出一个真实 Chrome 窗口**
3. 在窗口里扫码登录小红书创作者中心
4. 登录态写进 `data/browser_profiles/publish_xiaohongshu`，**以后发布不用再登录**
5. 再触发发布：内容填好后窗口保持打开，你确认无误点「发布」

> 全自动（`publish_strategy=auto`）模式下会代你点发布按钮，建议在无头+登录态稳定后再开。

## 六、为什么不选另外两条路

- **「把 scrapling 装进 .venv 就行」**：只解决依赖缺失。一次性上下文、截图拿不到、71 秒冷启动这三条是 StealthyFetcher 的固有设计，装上也照样跑不通半自动；而且它还要再拖一份 patchright 浏览器二进制。现在的实现已完全不需要 scrapling。
- **「改用小红书官方 API」**：创作者开放平台的发布 API 需要企业资质审核，个人号拿不到，短期不可行。

## 八、遗留建议（本次未改）

1. `qr_worker.py` 扫码登录仍写 `storage_states/*.json`（独立浏览器），建议改成复用 `publish_{platform}` profile，登录一次两边都生效
2. `app/platform_spider/*`（采集链路）顶层 `from scrapling.spiders import Spider`，而 `.venv` 里没有 scrapling——采集功能大概率也是瘫的，需要单独处理（要么装依赖，要么也迁到 playwright）
3. 平台选择器（如 `input[placeholder*='标题']`）是脆弱匹配，现在失败会体现在 `fill_errors` 里，改版后能第一时间定位
4. 系统 `C:\Python312` 与 `.venv` 依赖各缺一块，建议统一：`./.venv/Scripts/pip install scrapling`，别再往系统 python 里装东西
