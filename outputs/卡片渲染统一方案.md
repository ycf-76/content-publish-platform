# 卡片制作规范化方案 v2

> v1（2026-10-07 上午）方向错了：在下游的渲染组件和配色上打补丁，没解决根子问题。
> **v2 主线 = 入口规范化**：LLM 接到图文任务时，先用澄清卡让用户选骨架与风格，再开工。
> 下游（渲染组件收敛、容器配色）降为第二篇章，仍然要做，但不是主线。
>
> 参照系：`D:\技术博客\Easel\Easel\skills\openclaw\card-design\`
>
> 已拍板：① 骨架粒度 = **整套骨架序列（recipe）** ② 风格库 = **扩到 9 套 + 中文命名**
> ③ 时机修正为 **`when=missing` + 常驻切换器**（原"每次都问"会烦熟练用户）
>
> **产品判断（大哥提出两难后定的，是本方案的地基）**：
> - 用户拍板的真问题不是"烦"，是**模板膨胀后选择过载** —— 解法不是限制模板，是**把用户和模板隔开**：
>   用户只面对锁死 ≤7 个的意图层，模板库在底层随便长。
> - LLM 决策的真问题不是"选错"，是**不可预期** —— 同样输入两次给不同结果，用户形不成心智模型。
> - 因此：**当切换成本趋近于零时，事前选择的精度要求就大幅下降。**
>   我们有结构化 deck（内容独立于版式），「换骨架」可做到内容零丢失 —— 这是 Easel 做不到的。
>   所以与其让用户事前从 N 个模板里选准，不如让 LLM 先出成品，把「换一套」做成一等公民。

## 第一篇：入口规范化（主线）

### 1. 参照 Easel 得到的核心结论

Easel 的卡片渲染本身很朴素（`skills/shared/scripts/render_card.py`，HTML → PNG，所有 card-* skill 共用）。
它真正值钱的是 `card-design` 这套**设计系统**：

| 文件 | 作用 | 我们照搬什么 |
|---|---|---|
| `styles.md` | 9 种命名风格，每种锁死字体 + hex + 版式性格 + 适用场景 | ⭐ **五步流程第 1 步就是让用户选风格** |
| `card-recipes.md` | 骨架库（封面/账本/管线/对比/矩阵/数据/金句/收尾），**每个带最小密度线** | ⭐ 骨架要有最小密度线，不能空跑 |
| `layout-laws.md` | 填满 ≥75%、空白带 ≤15%、4 带密度自检、欠填/溢出修正阶梯 | 我们有 `audit.py`，需对齐判据 |
| `anti-ai-slop.md` | 禁 emoji 当图标、禁蓝紫渐变、禁玻璃拟态、禁居中一切 | 已有意识，可补进 composer prompt |
| `scripts/card_audit.py` | 渲染后硬门禁，FAIL 按修正阶梯重渲 | 我们有 `audit_page`，等价物 |

**Easel 的模型**：LLM 自由写 HTML，但**风格与骨架由用户拍**，事后靠 audit 兜底。
**我们的模型**：LLM 产 plan → `composer.py:286-344` 规则映射成 layout_id → 后端编译 HTML。

**我们比 Easel 强的一点，别丢**：我们有结构化 deck，`set_layout` / `set_theme` / 改块文本都是单页级可编辑的；Easel 出图即死的 PNG。所以方案是**两级**：前置让用户选整套骨架，事后仍可单页微调。

### 3. 设计

#### 3.1 整套骨架序列（recipe）— 新增概念

用户脑子里想的是"我要干货清单型还是步骤教程型"，不是"第 3 页用 bento 还是 ledger"。
所以澄清卡给的是**整套组合**，不是单页版式。

| recipe_id | 中文名 | 适用 | 页序列（版式族） |
|---|---|---|---|
| `knowledge_list` | 干货清单型 | 知识 / 科普 / 清单 | 封面 + 账本×N + 收尾 |
| `tutorial_steps` | 步骤教程型 | 教程 / 方法 / 流程 | 封面 + 步骤流程 + 收尾 |
| `data_insight` | 数据解读型 | 数据报告 / 调研 | 封面 + 数据大数 + 矩阵 + 收尾 |
| `opinion_quote` | 观点金句型 | 情感 / 观点 / 书评 | 封面 + 金句 + 账本 + 收尾 |
| `compare_pick` | 对比选购型 | 测评 / 选购 / 避坑 | 封面 + 对比表 + 账本 + 收尾 |
| `timeline_story` | 时间线叙事型 | 经历 / 复盘 / 成长 | 封面 + 时间线 + 收尾 |

**recipe 是软约束**：它锁定"用哪几个版式族"和**顺序**，页数仍由内容量决定（沿用现有 `plan.sections` 驱动）。
每条 recipe 带：中文名 + 一句话 + 适用场景 + **最小密度线**（沿用 `audit_page`）+ `preview_url`。

**数量锁死 6 个，不再增加**（7±2）。将来要加模板，加在底层的 layout_id，不动这一层 ——
这是"模板多了不好处理"的结构性解法。

**recipe 的介入点主要在 `_plan` 的 prompt**：告诉 LLM "用户选了干货清单型，优先把内容组织成 list"，
让内容**按骨架生成**，而不是事后把内容硬套进版式（硬套必然出现密度不够/溢出）。

#### 3.3 澄清字段声明

在 `ComposeCardDeckSkill` 上加 `clarify_meta`（照 `copywrite_builder.py:85-123` 的写法）：

```python
clarify_meta = {
    "card_recipe": ClarifyFieldMeta(
        hint="这套卡片用哪种骨架？",
        when=ClarifyWhen.missing,         # 只在没偏好时问，选完记住，之后不打断
        question_type=QuestionType.single_choice,
        default="knowledge_list",
        auto_default=True,                # 用户不理会 → 走默认，不阻塞
        options=[... 6 个 recipe，每个带 preview_url ...],
    ),
    "card_theme": ClarifyFieldMeta(
        hint="视觉风格选哪个？",
        when=ClarifyWhen.missing,
        question_type=QuestionType.single_choice,
        default="ink",
        auto_default=True,
        options=[... 9 套主题，每个带 preview_url ...],
    ),
    "card_image_layout": ClarifyFieldMeta(
        hint="图片怎么用？",
        when=ClarifyWhen.missing,
        question_type=QuestionType.single_choice,
        default="top",
        options=[顶图封面 / 右图正文 / 全图覆字，带 preview_url],
    ),
}
```

**前端零改动**：`ChatClarificationCard.vue` 的 `single_choice` 分支已经渲染 `opt.preview_url`（L30）。
（`image_select` / `text_input` 两种题型前端没实现，本轮不用，后续可补。）

#### 3.4 机制链路（全都现成的，不用新造）

```
用户说"做个 XX 图文卡"
  → 意图识别命中 ComposeCardDeckSkill（trigger_words 已有"做图文/卡片/知识卡"）
  → loop.py:2210+ 发现 clarify_meta 有未回答字段 → Guardian 之前插澄清
  → clarification_graph.py 收集 → 依赖图 → 分批（每批 5 题）→ 推前端
  → 用户点选 → compile_clarification_result → 注入 WorkflowState
  → compose_deck(recipe_id=..., theme_id=..., image_layout=...) → 制作
```

`prompt_skills.py:185-202` 还支持从 SKILL.md frontmatter 的 `clarify_schema` 自动注入 ——
如果卡片 skill 走 prompt-driven，连 Python 都不用改。

#### 3.5 骨架预览图

`preview_url` 要显示**真实渲染效果**，不能是示意图（否则用户选完发现货不对板）。

做法：离线用 `export.py::render_png_pages()`（Playwright + 项目自带 `pw-browsers/chromium-1228`）
给每个 recipe / 每套主题渲染一次**示例卡**（假内容），产物落到 `static/recipe-preview/` 当静态资源。
首次生成一次即可，之后是纯静态文件。

> 注意：`export.py:22` 那个浏览器路径目录名是 `pw-browsers `（**带尾空格**）。

#### 3.6 常驻切换器（本方案的重点，不是可选项）

澄清卡只是防守（保证首次不盲猜），**真正的可控感来自成品上的常驻切换器**：

- 成品卡片上直接放「换骨架 / 换风格」两个入口（**不是埋在快速编辑器里**）
- 每个入口带**真实渲染的缩略图**供选（复用 3.5 的预览图能力）
- 切换后**内容零丢失** —— deck 是结构化的，内容是 block，换版式只是换壳
- 复用现成的 `set_layout` / `set_theme` 后端能力，前端要做的是让它**一键可达 + 带预览**

> 这条是对 Easel 的差异化。它出图即死 PNG，改一个字都要重跑 LLM；我们可以换壳不换内容。

**落地时发现的两个机制约束（写代码前必须知道）**：

1. **澄清字段名必须与工具入参名一致** —— `loop.py` Stage 0 用 `_fname in arguments` 判断
   「LLM 是否已明确」，名字对不上时 LLM 传了参数仍会被拦下问一遍，且澄清结果灌不进工具入参。
2. **`auto_default=True` 的真实语义是「不打断」** —— 注入默认值继续执行，只推一张非阻塞建议卡。
   所以「真正让用户拍板」必须用 `False`。本方案的取舍：
   骨架 / 风格 = `False`（核心价值，第一次必须选）；图片用法 = `True`（技术性强，走默认）。
   配合 `when=missing` 的「已答过就跳过」判定，天然实现「第一次问、之后记住」。

### 5.1 七个渲染点收敛成一个组件

同一个 iframe 缩放逻辑抄了 7 遍（缩略算法、圆角、边框、底色各不相同，`fixViewport` 正则也抄了 2 份）：

| `components/chat/ContextSidebar.vue` | 117 |

| `components/workbench/SidebarNav.vue`（同文件抄 3 遍） | 15 |
| `components/chat/creation/WorkPreview.vue` | 10 |
| `components/chat/markdown-renderer.ts` | — |

**做法**：新增 `components/card/CardFrame.vue` + `card-frame.ts`（`fixViewport` / `computeScale`），
7 处替换为一行 `<CardFrame>`。容器样式 100% 走 `--card-frame-*` 变量，零硬编码。
**这一篇必须先做再做配色**，否则同一处改七遍。

### 5.2 配色：三层分离

```
内容层  后端 THEMES        → 决定出图，绝不受 App 明暗影响
容器层  --card-frame-*     → 边框/底/圆角/骨架/按钮，随 App 主题走
场景层  --ma-* / --dsh-*   → 只负责给容器变量赋值，组件不感知场景
```

**P0 bug**：`renderer.py:72-77` 的 `.image_bg_overlay` 硬编码 `background:#23323c` + 白字 + 固定渐变，
不走 `var(--bg)`/`var(--text)` —— 切任何主题，蒙层页永远同一套青灰底白字。
修法：给 `THEMES` 每套补一组反色 token `--on-image-bg/text/shade`，不能直接换 `var(--bg)`（浅色主题下白字会瞎）。

**主色跨模式不一致**：`_theme-vars.css` 亮色 `#FF2442`（红），`.dark` 下变 `#3B6CF6`（蓝）。建议统一回红系。

### 5.3 缩略图 PNG 化

后端已有 `render_png_pages()`，但只用于导出 zip。加 thumb 接口 + 缓存后：
- 侧栏几十个 iframe 全变 `<img>`，性能归零
- **消除「预览用你机器的字体、出图用 Chromium 字体」的差异** —— `Noto Serif CJK SC` 两端不一定都有
